# QueueWNK — ระบบแจ้งเตือนคิวผ่านหมอพร้อม

เฝ้าดูฐานข้อมูล HOSxP แล้วส่งแจ้งเตือนคิวไปยังผู้รับบริการผ่าน MOPH Alert (LINE OA หมอพร้อม + แอปหมอพร้อม)

## ฐานข้อมูล

มีสองฐานที่ไม่เกี่ยวกัน

| | |
| --- | --- |
| **HOSxP** | ของโรงพยาบาล อ่านอย่างเดียว ไม่ผ่าน Lucid เลย |
| **แอปเรา** | MariaDB ใน container เก็บ config, snapshot คิว, บันทึกการส่ง |

เลือก MariaDB ให้ตรงกับที่โรงพยาบาลใช้อยู่ (production เป็น MariaDB 12.3.2 แบบ master-master)
ทีม IT จะได้ดูแล engine เดียว ใช้ขั้นตอน backup / restore / monitoring ชุดเดิมที่มีคนรู้อยู่แล้ว
ซึ่งสำคัญกว่าความสะดวกตอนเขียนโค้ด เพราะระบบต้องอยู่ผ่านการเปลี่ยนคนดูแล

## หลักการที่ยึดไว้

**ไม่เขียนอะไรลงฐาน HOSxP เลย** ไม่ใส่ trigger ไม่สร้างตาราง ไม่อัปเดต flag
สถานะทั้งหมด (snapshot คิว, กันส่งซ้ำ, log) เก็บในฐานของแอปเอง

การเข้าถึง HOSxP ผ่าน [`HosxpClient`](app/services/hosxp_client.ts) ซึ่งเป็น mysql2 ดิบ
ที่ปฏิเสธ SQL ทุกอย่างที่ไม่ใช่การอ่านตั้งแต่ในโค้ด **ไม่เอา HOSxP มาเป็น connection
ใน Lucid โดยตั้งใจ** เพราะจะมี migration runner และ model ที่ `save()` ได้ชี้ไปที่ฐาน
โรงพยาบาลทันที พลาดครั้งเดียวก็เสียหาย สิทธิ์ระดับ MySQL เป็นด่านที่สอง

## ติดตั้ง

> 📘 **เพิ่งเคยติดตั้งครั้งแรก อ่าน [คู่มือติดตั้ง](docs/install.md) แทน**
> มีตั้งแต่ของที่ต้องขอล่วงหน้า สเปกเครื่อง ลำดับการตั้งค่า วิธีเปิดใช้จริงแบบไม่ให้
> ผู้ป่วยได้รับข้อความผิด และตารางแก้ปัญหาที่เจอบ่อย
> หัวข้อนี้เป็นคำสั่งล้วน ๆ สำหรับคนที่รู้อยู่แล้วว่ากำลังทำอะไร

ต้องมี **Docker** อย่างเดียว ไม่ต้องลง Node ไม่ต้องลง MariaDB ไม่ต้องมีซอร์ส

ใช้ไฟล์ 3 อย่าง — `queuewnk-<รุ่น>-images.tar.gz` · [`compose.prod.yml`](compose.prod.yml) · [`.env.example`](.env.example)
เอามาไว้โฟลเดอร์เดียวกัน

### 1. โหลด image เข้า Docker

```bash
docker load -i queuewnk-v0.1.0-images.tar.gz
```

ต้องขึ้นสองบรรทัด — `Loaded image: queuewnk:0.1.0` และ `Loaded image: mariadb:12`

### 2. ตั้งค่า

กรอกแค่ 2 บรรทัดบนสุดของ `.env` ที่เหลือปล่อยไว้ **แต่ต้องเรียงตามนี้**

```bash
cp .env.example .env
```

1. กรอก `DB_PASSWORD=` ก่อน — ตั้งเองอะไรก็ได้ ระบบใช้เอง ไม่ต้องจำ
   **ข้ามไม่ได้** เพราะ Docker อ่านไฟล์ตั้งค่าทั้งไฟล์ก่อนเริ่มทำงาน
   คำสั่งข้อถัดไปจะไม่ยอมรันถ้าบรรทัดนี้ยังว่าง
2. รัน `generate:key` แล้วเอาค่าที่พิมพ์ออกมาใส่ `APP_KEY=`

```bash
docker compose -f compose.prod.yml run --rm --no-deps web node ace generate:key
```

> ⚠️ **`APP_KEY` ตั้งครั้งเดียวแล้วห้ามเปลี่ยน** เป็นกุญแจที่ใช้เข้ารหัสรหัสผ่าน HOSxP
> และ secret ของ MOPH ก่อนเก็บลงฐาน เปลี่ยนเมื่อไรค่าเดิมถอดไม่ออก ต้องกรอกใหม่ทุกหน้า
> **เก็บสำรองไว้คู่กับ backup ฐานข้อมูล** ไม่งั้น restore มาแล้วใช้ไม่ได้

### 3. เปิดระบบ

```bash
docker compose -f compose.prod.yml up -d
```

```bash
docker compose -f compose.prod.yml exec web node ace migration:run --force
```

```bash
docker compose -f compose.prod.yml exec web node ace admin:create you@hospital.go.th 'รหัสผ่านอย่างน้อย8ตัว' 'ชื่อ นามสกุล'
```

เปิด http://localhost:3333 แล้วล็อกอิน

### 4. สร้าง user อ่านอย่างเดียวบน HOSxP

รันบนเครื่องฐานข้อมูลของโรงพยาบาล **ไม่ใช่ในคอนเทนเนอร์**

```sql
CREATE USER 'queuewnk_ro'@'%' IDENTIFIED BY 'ตั้งรหัสเอง'; GRANT SELECT ON hos.* TO 'queuewnk_ro'@'%'; FLUSH PRIVILEGES;
```

จำกัด `@'%'` ให้แคบลงเป็น subnet ของเครื่องที่รันระบบนี้ได้ยิ่งดี — ปุ่มทดสอบในหน้า
`/settings/hosxp` จะบอก IP ที่คอนเทนเนอร์ออกไปมาให้ในข้อความ error

### 5. สำรวจฐานของโรงพยาบาลตัวเองก่อน

**อย่าข้ามขั้นนี้** ระบบนี้พัฒนากับ HOSxP ของโรงพยาบาลเดียว สิ่งที่จริงที่นั่นอาจไม่จริงที่อื่น

```bash
docker compose -f compose.prod.yml exec web node ace hosxp:discover
```

```bash
docker compose -f compose.prod.yml exec web node ace hosxp:probe-queue
```

| ตรวจอะไร | ทำไม |
| --- | --- |
| **ตารางคิวไหนมีข้อมูล** | ที่ต้นทางใช้ `ovst_queue_server` ส่วน `opd_queue` ว่างเปล่า **ของคุณอาจกลับกัน** |
| **charset อ่านภาษาไทยออกไหม** | HOSxP v3 มักเป็น `tis620` ถ้าตั้งผิดชื่อผู้ป่วยจะเป็นตัวขยะแล้วส่งออกไปทั้งอย่างนั้น |
| **นาฬิกาต่างจาก DB กี่วินาที** | เกิน 60 วินาทีการตรวจจับด้วยเวลาจะพลาด |
| **`cid` ครบ 13 หลักกี่ %** | ผู้ป่วยที่ไม่มีเลขบัตรจะส่งแจ้งเตือนไม่ได้เลย |

> ⚠️ **ถ้าตารางคิวไม่ตรงกัน ต้องแก้ SQL ใน [queue_poller.ts](app/services/queue_poller.ts) เอง**
> ซึ่งทำใน image ไม่ได้ ต้องไปใช้[วิธีติดตั้งจากซอร์ส](#ติดตั้งจากซอร์ส-สำหรับคนที่จะแก้โค้ด)แทน
> ตอนนี้ยังไม่ได้ทำให้เลือกตารางจากหน้าเว็บได้

### 6. ค่อยเปิดทีละห้อง

ตั้งต้น dry run เปิดอยู่และปิดทุกห้อง เปิดทีละห้องแล้วดูใน `/log` ว่าเลขคิวตรงกับบัตรคิวจริงไหม
ก่อนปิด dry run

## อัปเดต

```bash
docker load -i queuewnk-v0.1.1-images.tar.gz
```

แก้เลขรุ่นที่ `QUEUEWNK_IMAGE` ใน `.env` ให้ตรงกับรุ่นใหม่ (ถ้าไม่มีบรรทัดนี้ให้เพิ่มเข้าไป) แล้ว

```bash
docker compose -f compose.prod.yml up -d
```

```bash
docker compose -f compose.prod.yml exec web node ace migration:run --force
```

จบ **ไม่มีขั้นตอน restart ให้ลืม** เพราะ `up -d` สร้าง container ใหม่จาก image ใหม่ให้เอง
และ `.env` กับฐานข้อมูลไม่ถูกแตะ ค่าที่ตั้งไว้ในหน้าเว็บอยู่ครบ

**image รุ่นเก่ายังอยู่ในเครื่อง** ย้อนกลับได้ทันทีถ้ารุ่นใหม่มีปัญหา แค่แก้เลขรุ่นใน `.env`
กลับแล้ว `up -d` ใหม่ — แต่ migration ไม่ย้อนตามให้ **อ่าน [CHANGELOG.md](CHANGELOG.md) ก่อนอัปเดตเสมอ**

## ติดตั้งจากซอร์ส (สำหรับคนที่จะแก้โค้ด)

จำเป็นเมื่อต้องแก้โค้ด เช่นโรงพยาบาลที่ใช้ตารางคิวคนละตัว หรือจะส่ง PR กลับ

```bash
git clone https://github.com/Pandajob/QueueWNK.git queuewnk && cd queuewnk && cp .env.example .env
```

```bash
docker compose run --rm --no-deps web node ace generate:key
```

ตัวนี้**เขียน `APP_KEY` ลง `.env` ให้อัตโนมัติ** (ต่างจากทางข้างบนที่ image ไม่มี `.env`
อยู่ข้างในให้เขียน จึงพิมพ์ออกมาให้คัดลอกเอง) เหลือกรอก `DB_PASSWORD=` อย่างเดียว แล้ว

```bash
docker compose up -d && docker compose exec web node ace migration:run --force
```

จากนั้นทำขั้นที่ 3–6 ข้างบนต่อ โดยตัด `-f compose.prod.yml` ออกจากทุกคำสั่ง

**อัปเดต** — `git pull` แล้ว `docker compose build && docker compose up -d` ตามด้วย
`migration:run --force` และ **`docker compose restart web worker notify`**

> ⚠️ **ต้อง `restart` ทุกครั้งหลัง `git pull`** โค้ดถูก mount เป็น bind mount และบน Windows
> สัญญาณไฟล์เปลี่ยนไม่ทะลุเข้าคอนเทนเนอร์ ตัวรีโหลดอัตโนมัติจึงไม่ทำงาน ที่หลอกกว่านั้นคือ
> ไฟล์ `.edge` ถูกอ่านใหม่ทุกคำขออยู่แล้ว **หน้าเว็บจะดูเหมือนอัปเดตแล้วทั้งที่โค้ดยังเป็นตัวเก่า**
> อาการคลาสสิกคือกดบันทึกแล้วค่ากลับมาเป็นเดิม

## สร้างไฟล์แจก (สำหรับผู้ดูแล repo)

```bash
docker build --target production -t queuewnk:0.1.0 .
```

```bash
docker save queuewnk:0.1.0 mariadb:12 | gzip -6 > queuewnk-v0.1.0-images.tar.gz
```

**ต้องใส่ `mariadb:12` ไปด้วยเสมอ** ไม่งั้นปลายทาง `up -d` แล้วค้างรอดาวน์โหลดฐานข้อมูล
ได้ไฟล์ราว 181 MB

ส่งคู่กับชุดตั้งค่าเล็ก ๆ ที่รวม `compose.prod.yml` · `.env.example` · `install.md`
และไฟล์ `READ-ME-FIRST.txt` ฉบับย่อ 5 ขั้นตอน

```bash
python -c "import zipfile,os; z=zipfile.ZipFile('queuewnk-v0.1.0-setup.zip','w',zipfile.ZIP_DEFLATED); [z.write(f,'queuewnk-setup/'+os.path.basename(f)) for f in ['compose.prod.yml','.env.example','docs/install.md']]; z.close()"
```

**อย่าใช้ `Compress-Archive` ของ PowerShell** มันเขียนตัวคั่นพาธเป็น backslash
ซึ่งผิดมาตรฐาน zip แตกบน Linux หรือ macOS แล้วขึ้น warning และได้โครงไฟล์เพี้ยน

ตรวจว่าไฟล์ใช้ได้จริงก่อนส่ง โดยลบ image ออกจากเครื่องแล้วโหลดกลับ

```bash
docker rmi queuewnk:0.1.0 && docker load -i queuewnk-v0.1.0-images.tar.gz
```

## หน้าเว็บ

**แถบบนเลือกระบบ · sidebar เป็นเมนูของระบบนั้น**

| ระบบ | สำหรับ | เมนู |
| --- | --- | --- |
| **Alert** | แจ้งเตือนคิวผู้ป่วยรายคน | บันทึกการส่ง · ทดสอบส่ง · ข้อความแจ้งเตือน · การส่ง · MOPH Alert |
| **Notify** | แจ้งเตือนกลุ่มเจ้าหน้าที่ | แดชบอร์ด · ตารางเวลา · CDCU · เทมเพลตข้อความ · รายการข้อมูล · กลุ่ม LINE · ประวัติการส่ง · ประวัติการแก้ไข |
| **CCM** | บรอดแคสต์หมอพร้อม | ภาพรวม (ยังไม่ได้ต่อ API) |
| **Monitor** | สุขภาพเครื่องและฐานข้อมูล | สถานะ · เทียบเครื่องฐานข้อมูล · แจ้งเตือนทีมงาน |
| **ระบบ** | ตั้งค่าที่ใช้ร่วมกัน | ภาพรวม · ฐานข้อมูล HOSxP · ผู้ใช้ |

แท็บ **Monitor** รวมสามหน้าที่เคยกระจายอยู่คนละแท็บ (สถานะอยู่ใต้ Alert · แจ้งเตือนทีมงาน
อยู่ใต้ Notify · เทียบเครื่องฐานข้อมูลอยู่ใต้ ระบบ) ทั้งที่คนเปิดคือทีมไอทีชุดเดียวกัน และไม่มีหน้าไหน
เกี่ยวกับ “จะส่งอะไรหาใคร” ซึ่งเป็นเกณฑ์แบ่งของอีกสามแท็บ **URL ไม่ได้เปลี่ยนตาม** bookmark เดิมใช้ได้
หน้าแรกของ Alert เปลี่ยนจาก `/status` เป็น `/log`

โครงเมนูอยู่ที่ [app/services/navigation.ts](app/services/navigation.ts) ที่เดียว
แต่ละหน้าใส่แค่ `active: '<key>'` แล้ว layout ย้อนหาเองว่า key นั้นอยู่ระบบไหน
มีเทสต์คุมว่า **ทุกหน้าที่ใช้ layout หลักต้องมี key อยู่ในเมนู** และ **key ห้ามซ้ำข้ามระบบ**
หน้าใหม่ที่ลืมใส่เมนูจะสอบตกทันที ไม่ต้องรอให้ผู้ใช้เจอ sidebar หายทั้งแถบ

| หน้า | ทำอะไร |
| --- | --- |
| `/status` | สถานะ HOSxP / MOPH / worker แบบ tile พร้อมรายละเอียด |
| `/log` | ทุกรายการที่ระบบตั้งใจส่ง พร้อมผลลัพธ์และปุ่มส่งใหม่ |
| `/test` | เลือกเคส กรอกข้อมูลสมมติ ดู payload แล้วส่งจริงได้ |
| `/settings` | หน้ารวมทางเข้าการตั้งค่า บอกสถานะแต่ละส่วน |
| `/settings/hosxp` | ค่าเชื่อมต่อฐาน HOSxP + ปุ่มทดสอบ |
| `/settings/db-sync` | เทียบว่าเครื่องฐานข้อมูลทุกเครื่องมีข้อมูลตรงกันไหม + แจ้งเข้ากลุ่ม |
| `/settings/moph` | client-key / secret-key + ปุ่มทดสอบ |
| `/settings/notify` | เลือกกลุ่ม LINE ที่จะรับแจ้งเตือนสถานะระบบ + เรื่องที่จะเตือน |
| `/ccm` | อธิบาย MOPH CCM และขอบเขตที่ API ทำได้ (ยังไม่ได้ต่อ) |
| `/settings/templates` | ออกแบบข้อความแจ้งเตือนทั้ง 4 เคส |
| `/settings/poller` | เปิด/ปิด dry run · ช่วงเวลางดส่ง · เกณฑ์ใกล้ถึงคิว · ห้องที่จะแจ้ง |
| `/settings/users` | เพิ่ม แก้ไข ลบผู้ใช้ที่เข้าหน้าตั้งค่าได้ |

หน้า `/status` ดู heartbeat จากตาราง `worker_heartbeats` ที่ `queue:watch` เขียนทุกรอบ
ถ้าไม่มีสัญญาณเกิน 90 วินาทีจะขึ้นว่าขาดการติดต่อ — จับได้ทั้งกรณี process ตายและกรณีค้าง

ผู้ใช้ทุกคนมีสิทธิ์เท่ากัน ระบบกันไม่ให้ลบบัญชีที่กำลังใช้งานอยู่ และกันไม่ให้ลบคนสุดท้าย
(ไม่งั้นจะไม่มีใครเข้าหน้าตั้งค่าได้อีกเลย)

### `/settings/templates` — ออกแบบข้อความ

เอกสารแบ่ง template เป็น 6 แบบ แต่แบบ 2/3 และ 5/6 ใช้ค่า `template` เดียวกัน
ต่างกันแค่มี url ตรวจสอบคิวหรือไม่ ระบบจึงรวมเหลือ **4 เคส** แล้วให้ช่องลิงก์เป็นตัวตัดสิน

| เคส | ตัวยึดที่ใช้ได้ |
| --- | --- |
| ยินดีต้อนรับ | `{name}` |
| แจ้งเตือนคิว | `{name}` `{queue_no}` `{hn_no}` `{service}` `{url}` |
| ใกล้ถึงคิวของคุณแล้ว | เพิ่ม `{queue_waiting}` · ตั้ง threshold ได้ |
| คิวของท่านมีการเปลี่ยนแปลง | เหมือนเคสใกล้ถึงคิว |

ใส่ตัวยึดที่เคสนั้นไม่รองรับจะถูกปฏิเสธตอนบันทึก ไม่ปล่อยผ่านแล้วให้ผู้ป่วยเห็น `{xxx}` ติดไป

แก้ทั้ง `message_html` แยกจากข้อความบนการ์ด เพราะปลายทางไม่ได้สร้างเนื้อหาส่วนนั้นให้
ต้องเขียนซ้ำเอง (ข้อจำกัดของ API ไม่ใช่ของระบบนี้)

### `/test` — ทดสอบส่ง

เลือกเคส → กรอกข้อมูลสมมติ → **ดู payload ที่จะส่ง** (ไม่ยิงออกไปเลย) → **ส่งจริง**

ปุ่มส่งจริงต้องกรอกเลขบัตร 13 หลักเองและมี confirm ที่แสดงเลขบัตรแบบปิดบัง
**ข้อความจะไปถึง LINE หมอพร้อมของเจ้าของเลขบัตรนั้นจริง** ใช้เลขของตัวเองหรือของ
เจ้าหน้าที่ที่ยินยอมแล้วเท่านั้น ทุกครั้งที่ส่งจะถูกบันทึกลง log พร้อมเลขบัตรแบบปิดบัง

ต่างจากปุ่มทดสอบในหน้า `/settings/moph` ที่ใช้เลขบัตรสมมติ `0000000000000`
และไม่มีข้อความถึงใครเลย

### `/settings/hosxp`

กรอก host / port / database / user / password / charset
ปุ่ม **ทดสอบการเชื่อมต่อ** ใช้ค่าที่กำลังกรอกอยู่ ยังไม่บันทึก จึงลองหลาย charset ได้ รายงาน

- เวอร์ชัน MySQL และ charset ของฐาน
- ส่วนต่างเวลากับ DB — ถ้าเกิน 60 วินาทีจะเตือน เพราะการ poll ด้วย timestamp จะพลาด
- สิทธิ์ของ user — เตือนถ้าเขียนได้
- **ตัวอย่างชื่อผู้ป่วยภาษาไทย** ให้เห็นกับตาว่า charset ถูก (HOSxP v3 มักเป็น `tis620`)
  ถ้าอ่านออกมาเป็นตัวขยะแล้วปล่อยผ่าน ชื่อขยะจะถูกส่งเข้า MOPH Alert ตรง ๆ

ต้องสร้าง read-only user บน MySQL ก่อน โดยระบุ host ให้ตรงกับ IP ที่ container ออกไป
(ปุ่มทดสอบจะบอก IP นั้นมาในข้อความ error)

```sql
CREATE USER 'queuewnk_ro'@'%' IDENTIFIED BY 'ตั้งรหัสเอง'; GRANT SELECT ON hos.* TO 'queuewnk_ro'@'%'; FLUSH PRIVILEGES;
```

### `/settings/db-sync` — เทียบว่าเครื่องฐานข้อมูลตรงกันไหม

โรงพยาบาลมี MariaDB สามเครื่องและทำ replication กันอยู่ หน้านี้ถามทุกเครื่องด้วย
คำถามเดียวกันแล้วดูว่าตอบเหมือนกันไหม ถ้าไม่เหมือนจะบอกทีมงานเข้ากลุ่ม LINE

**ทำไมไม่ดู `SHOW SLAVE STATUS` ซึ่งตรงกว่า** — user ที่ระบบใช้มีสิทธิ์ `SELECT`
อย่างเดียว อ่าน status ของ replication ไม่ได้ (ต้องมี `REPLICATION CLIENT`) และเรา
ตั้งใจไม่ขอสิทธิ์เพิ่มกับฐานโรงพยาบาล จึงวัดจาก**ผลลัพธ์**แทน**กลไก** คือนับแถวของวันนี้
ในตารางที่ใช้งานจริงแล้วเอามาเทียบกัน ซึ่งตอบคำถามที่อยากรู้จริง ๆ ว่า
“ถ้าไปดูจากเครื่องนี้จะเห็นเท่ากันไหม”

| นับอะไร | จากตาราง | กรองด้วย |
| --- | --- | --- |
| ผู้รับบริการวันนี้ | `vn_stat` | ช่วง `vn` ของวันนี้ |
| ทะเบียนตรวจ | `ovst` | ช่วง `vn` |
| คิวห้องตรวจ | `ovst_queue_server` | ช่วง `vn` |
| รายการยา/ค่าใช้จ่าย | `opitemrece` | ช่วง `vn` |
| ผู้ป่วยในรับใหม่ | `ipt` | `regdate = CURDATE()` |

ทุกคำถามกรองด้วยช่วง `vn` ซึ่งเป็น primary key ใช้เวลาเครื่องละ 3–6 มิลลิวินาที
**ไม่กรองด้วย `vstdate`/`date_visit` เพราะไม่มี index** จะกลายเป็นสแกนทั้งตาราง
300+ ms ทุกรอบ (ดู [docs/queue-detection.md](docs/queue-detection.md))

นอกจากตัวเลขยังเก็บ `hostname` · `server_id` · `read_only` · `log_bin` และ `NOW()`
ของแต่ละเครื่องมาเทียบนาฬิกาด้วย

#### สถานะ replication จาก GTID

`SHOW SLAVE STATUS` ต้องมี `REPLICATION CLIENT` ซึ่งเราไม่ขอ แต่ตัวเลขที่สำคัญที่สุด
อยู่ในที่ที่ user สิทธิ์ `SELECT` อ่านได้อยู่แล้ว

| อ่านจาก | บอกอะไร |
| --- | --- |
| `@@global.gtid_current_pos` | เครื่องนี้ทำ transaction ถึงลำดับไหน — ลบกันข้ามเครื่องได้ตรง ๆ |
| `@@global.gtid_slave_pos` | ลำดับที่รับมาจากต้นทาง |
| `SHOW GLOBAL STATUS` → `Slave_running` | สายรับข้อมูลยังเดินอยู่ไหม |
| `SHOW GLOBAL STATUS` → `Slaves_connected` | มีตัวตามต่อออกจากเครื่องนี้กี่เครื่อง |
| `SHOW GLOBAL STATUS` → `Slave_received_heartbeats` | เครื่องนี้เคยเป็นตัวตามจริงหรือเปล่า |

**GTID แม่นกว่าการนับแถวมาก** เพราะนับแถวบอกได้แค่ตารางที่เรานึกออกว่าจะนับ
ส่วน GTID นับทุก transaction ที่เกิดขึ้นในฐาน ตัวเลข `ตามหลัง N รายการ` มาจากตรงนี้
และเทียบแยกราย `gtid_domain_id` ไม่เอาลำดับข้าม domain มาลบกัน

**บทบาทของเครื่อง** เดาจาก `Slave_received_heartbeats` ไม่ใช่ `gtid_slave_pos`
เวอร์ชันแรกใช้ `gtid_slave_pos` แล้วเจอว่าเครื่องต้นทางก็มีค่านี้ค้างอยู่ (ตัวแปรไม่ถูกล้าง
เมื่อเปลี่ยน topology และ `log_slave_updates` พาลำดับวิ่งไปทั่ว) ผลคือไปเตือนว่า
“replication หยุด” ที่เครื่องต้นทางซึ่งไม่เคยมีสายรับตั้งแต่แรก — heartbeat นับเฉพาะตอนที่มี
สายรับต่ออยู่จริง เครื่องต้นทางจึงเป็น 0 ตลอด

หน้านี้จะวาด topology ที่ตรวจพบให้เอง ไม่ต้องกรอกว่าเครื่องไหนเป็นอะไร

**สิ่งที่มักเจอในของจริง** — ที่ซึ่งพัฒนาระบบนี้ขึ้นมามีสามเครื่องทำ replication กันอยู่
และ**ตัวตามทั้งสองเครื่องตั้ง `read_only = OFF`** คือเขียนลงตรง ๆ ได้ทั้งคู่ ซึ่งเป็น
สภาพที่พบได้บ่อยและเป็นทางที่ข้อมูลจะแยกกันโดยไม่มีใครรู้ตัว

ระบบขึ้นเรื่องนี้เป็น**ข้อสังเกต**บนการ์ด แต่**ไม่เตือน** เพราะเป็นความเสี่ยงเชิงตั้งค่า
ไม่ใช่เหตุการณ์ที่เพิ่งเกิด เตือนทุกรอบมีแต่จะถูกมองข้าม — เจอแล้วให้คุยกับ DBA ครั้งเดียวจบ

#### ตามหลัง กับ แยกทางกัน ไม่เหมือนกัน

| ผล | แปลว่า | ต้องทำอะไร |
| --- | --- | --- |
| **ตรงกัน** | ทุกเครื่องนับได้เท่ากัน | ไม่ต้องทำอะไร |
| **ตามหลัง** | เครื่องหนึ่งน้อยกว่า**ทุกตาราง** | replication lag ปกติ เดี๋ยวตามมาก็หาย |
| **แยกทางกัน** | เครื่อง A นำตารางหนึ่ง เครื่อง B นำอีกตารางหนึ่ง | **รอไปไม่หายเอง** ต้องให้ DBA ดู |
| **สายรับหยุด** | เคยเป็นตัวตามแต่ `Slave_running = OFF` | **เร่งด่วน** ยิ่งช้ายิ่งตามยาก |
| **ต่อไม่ได้** | ต่อเครื่องนั้นไม่ได้เลย | ดูสาเหตุในข้อความ |

ตามหลังนิดหน่อยเป็นเรื่องปกติ จึงมีเกณฑ์ให้ตั้งว่าต่างกันกี่แถว/กี่วินาที/กี่ transaction ถึงจะเตือน
แต่ **ต่อไม่ได้** · **แยกทางกัน** · **สายรับหยุด** เตือนทันทีไม่ว่าตั้งเกณฑ์ไว้เท่าไร — สามอย่างนี้
ไม่ใช่เรื่องที่รอแล้วหายเอง เช่นเดียวกับนาฬิกาที่ต่างกันเกิน 2 นาที (`vn` สร้างจาก
เวลาเครื่อง ต่างกันมากแล้วเลขซ้ำกันได้)

#### เรื่องการส่ง

เลือกได้ว่าจะส่งเป็นข้อความหรือการ์ด — ค่าตั้งต้นคือ **การ์ดเฉพาะรายงานประจำวัน
ส่วนเรื่องด่วนเป็นข้อความ**

| ตั้งเป็น | รายงานประจำวัน | เรื่องด่วน |
| --- | --- | --- |
| `ข้อความธรรมดาทุกครั้ง` | text | text |
| `การ์ดเฉพาะรายงานประจำวัน` (ตั้งต้น) | **การ์ด** | text |
| `การ์ดทุกครั้ง` | **การ์ด** | **การ์ด** |

เหตุผลที่ไม่ตั้งต้นเป็นการ์ดทุกครั้ง: ปลายทางดองการ์ดไว้ราว 19 นาที (ดูหัวข้อ
“การ์ด Flex เข้ากลุ่มช้ากว่าข้อความธรรมดามาก”) รายงานประจำวันช้า 19 นาทีไม่มีใคร
เดือดร้อน แต่ **“replication หยุดเดิน” ช้า 19 นาที คือข้อมูลแยกกันไปแล้วครึ่งชั่วโมง**

การ์ดเป็นโทนม่วง เปลี่ยนสีได้ในหน้าตั้งค่า โครงเป็น bubble ภาพรวม (แถบสรุป + กล่องรายเครื่อง
พร้อมป้ายบทบาทและตัวเลข GTID) แล้วต่อด้วย bubble ตารางเทียบข้อมูลวันนี้
ค่าที่น้อยกว่าเครื่องที่นำอยู่ทำสีส้ม

**การ์ดแตกใบเองเมื่อเนื้อหาล้น** — สามเครื่องที่มีปัญหาพร้อมกันเคยทำให้ใบเดียว 10,388 ไบต์
ทะลุเพดาน 10 KB แล้วปลายทางปฏิเสธทั้งข้อความ ตอนนี้ตัวสร้างวัดไบต์จริงแล้วขึ้นใบใหม่ให้
(ดู `db:sync-check` ที่พิมพ์ขนาดแต่ละใบออกมา) กลุ่มที่ปิดสวิตช์ `supports_flex`
จะได้ข้อความธรรมดาแทนอัตโนมัติ ข้อมูลครบเหมือนกัน

- `ไม่เตือนเรื่องเดิมซ้ำภายใน N นาที` — แต่ถ้า**อาการเปลี่ยน** (เมื่อกี้ตามหลัง ตอนนี้ต่อไม่ได้)
  จะเตือนทันทีไม่รอครบ
- `รายงานสรุปประจำวัน` — แก้ปัญหา “เงียบแปลว่าอะไร” ไม่มีข้อความเข้ามาเลยอาจแปลว่าปกติดี
  หรือแปลว่าตัวเฝ้าตายไปแล้วก็ได้ มีข้อความวันละครั้งจะแยกสองอย่างนี้ออก
- ไม่มีช่วงงดส่ง ต่างจาก CDCU — ฐานข้อมูลแยกทางกันตอนตีสามก็ยังอยากรู้ตอนตีสาม

#### ตั้งค่าเครื่อง

ช่อง user/รหัสของแต่ละเครื่องเว้นว่างไว้ = ใช้ค่าเดียวกับหน้า `/settings/hosxp`
เปลี่ยนแค่ host **ล้างช่อง Host แล้วบันทึก = ลบเครื่องนั้นออก**

ต้อง `GRANT SELECT` ให้ user เดียวกันบนทุกเครื่องที่จะเฝ้า ไม่งั้นจะขึ้นว่าต่อไม่ได้

```bash
docker compose exec web node ace db:sync-check
```

พิมพ์ตารางเทียบและข้อความที่จะส่ง **โดยยังไม่ส่ง** ใส่ `--send` ถ้าจะส่งจริง
ต่างจาก `hosxp:compare-hosts` ตรงที่ตัวนั้นให้พิมพ์ host เอาเองเพื่อ “เลือกเครื่องที่จะต่อ”
ส่วนตัวนี้อ่านรายชื่อจากที่ตั้งค่าไว้ และใช้เกณฑ์เดียวกับที่ worker ใช้ตัดสิน

### `/settings/moph`

กรอก Base URL / Client ID / Secret จาก CMS MOPH ALERTING เมนู “จัดการ Token”

ปุ่ม **ทดสอบ key** ยิงคำขอด้วยเลขบัตรสมมติ `0000000000000` แล้วอ่านคำตอบ

| คำตอบปลายทาง | แปลว่า |
| --- | --- |
| `401 client-key or secret-key incorrect` | key ผิด |
| `401 Hospital Logo is empty` | key ถูก แต่ยังไม่ได้อัปโหลดโลโก้ใน CMS — ส่งจริงจะไม่ผ่าน |
| `404 Error template` | key ถูก (แค่หาเลขบัตรไม่เจอ ตามคาด) |

ปลายทางตรวจ key ก่อนตรวจ cid เสมอ จึงตรวจ key ได้โดยไม่มีข้อความส่งถึงผู้ป่วยจริง

รหัสผ่านและ secret ทั้งหมดเข้ารหัสด้วย `APP_KEY` ก่อนลง DB และไม่แสดงกลับมาในฟอร์มอีก
**ถ้า `APP_KEY` ใน `.env` เปลี่ยน ค่าที่เก็บไว้จะถอดรหัสไม่ออก ต้องกรอกใหม่**

## ระบบ MOPH Notify

**คนละระบบกับ MOPH Alert** — Alert ส่งหาผู้ป่วยรายคนด้วยเลขบัตร ส่วน Notify ส่งเข้ากลุ่มแชท
LINE ที่มีคนอ่านหลายคน จึงเป็นช่องทางของ**เจ้าหน้าที่** ไม่ใช่ของผู้ป่วย

```
POST {baseUrl}/api/notify/send
Header: client-key, secret-key
Body:   { "messages": [ { "type": "text", "text": "..." } ] }
```

| หน้า | ทำอะไร |
| --- | --- |
| `/notify` | ภาพรวม — ยอดส่ง สถานะ worker รายการล่าสุด รายการที่ล้มเหลว |
| `/notify/schedules` | รอบส่งซ้ำ รายวัน/รายสัปดาห์/รายเดือน |
| `/notify/cdcu` | เฝ้าระวังเคส 506 + ดูเคสล่าสุดและสรุปรายโรค |
| `/notify/templates` | เขียนข้อความ ผูกชุดข้อมูล ดูตัวอย่าง และส่งเดี๋ยวนี้ |
| `/notify/datasets` | คำสั่งดึงข้อมูลจาก HOSxP ที่เอาไปเติมในข้อความ |
| `/notify/groups` | กลุ่ม LINE ปลายทาง — Client_ID / Secret และปุ่มทดสอบ |
| `/notify/history` | ทุกข้อความที่ส่ง พร้อมผลและข้อความเต็มตามที่ส่งจริง |
| `/notify/audit` | ใครแก้อะไรเมื่อไร |

worker แยกจากงานคิว — service `notify` รัน `node ace notify:watch` ตรวจทุก 60 วินาที
query ที่ผู้ดูแลเขียนเองจึงไม่มีทางไปถ่วงงานคิวซึ่งเป็นงานที่ผู้ป่วยรออยู่จริง

### รายการข้อมูล (datasets)

SQL ที่ผู้ดูแลเขียนเอง วิ่งผ่าน `HosxpClient` ตัวเดียวกับที่ระบบคิวใช้ ด่านความปลอดภัยสามชั้น

1. รับเฉพาะคำสั่งที่ขึ้นต้นด้วย `SELECT` / `SHOW` / `DESCRIBE` / `EXPLAIN` / `WITH`
   และปิด `multipleStatements` — ต่อคำสั่งที่สองด้วย `;` ไม่ได้
2. สิทธิ์ระดับ MySQL เป็น `GRANT SELECT` อย่างเดียว
3. ครอบ `SELECT * FROM (…) LIMIT 200` อีกชั้น (ยกเว้น `SHOW`/`DESCRIBE` ที่ครอบไม่ได้)

**สิ่งที่ยังกันไม่ได้คือ query ที่อ่านหนัก** — MariaDB ต้องใช้
`SET STATEMENT max_statement_time=… FOR SELECT …` ซึ่งขึ้นต้นด้วย `SET` แล้วโดนด่านที่ 1 ปฏิเสธ
ระบบจึงได้แค่วัดเวลาแล้วเตือนว่าช้า กด “ลองรัน” ดูก่อนเอาไปตั้งรอบส่งทุกวัน

ชื่อคอลัมน์ที่ query คืนมากลายเป็นตัวยึดในเทมเพลต — `{visits}` เอาค่าจากแถวแรก
ส่วน `{each}…{/each}` วนทุกแถว มี builtin ให้อีกชุด (`{date}` `{time}` `{rows}` …)
ตัวยึดที่ไม่มีค่าให้จะกลายเป็นค่าว่าง ไม่ปล่อย `{xxx}` ติดไปให้คนอ่านเห็น

ชื่อคอลัมน์ของการรันครั้งล่าสุดถูกจำไว้ใน `last_columns` เพื่อให้ตัวแก้ไขการ์ด
เสนอเป็น dropdown ได้ โดยไม่ต้องยิง query ใส่เครื่องโรงพยาบาลทุกครั้งที่เปิดหน้าแก้เทมเพลต

**ห้ามใส่ `CONVERT` แปลง charset** ท่าที่เจอบ่อยเวลาคัด SQL มาจาก HeidiSQL/Navicat คือ

```sql
CONVERT(CAST(CONVERT(k.department USING utf8) AS BINARY) USING tis620)
```

ท่านี้จำเป็นกับโปรแกรมที่ต่อฐานเป็น utf8 แต่ระบบนี้ต่อด้วย `TIS620_THAI_CI` อยู่แล้ว
ใส่เพิ่มจะกลายเป็นแปลงซ้ำ ได้ `OPD เธ�เธธเธ�เธ�เธฑเธ�...` แทน `OPD จุดซักประวัติ`
เรียกคอลัมน์ตรง ๆ พอ (มีคำเตือนไว้ในหน้าเพิ่มชุดข้อมูลแล้ว)

### เทมเพลตข้อความ — ธรรมดา หรือการ์ด Flex

เทมเพลตเลือกได้สองแบบ **ข้อความธรรมดา** กับ **การ์ด Flex**

การ์ดไม่ได้เก็บเป็น Flex JSON ดิบ แต่เก็บเป็น**รายการบล็อก** แล้วแปลงเป็น Flex ตอนส่ง
เพื่อให้ผู้ดูแลแก้จากหน้าเว็บได้โดยไม่ต้องรู้จัก schema ของ LINE
และถ้า LINE เปลี่ยนรูปแบบ แก้ที่ตัวแปลงจุดเดียว ไม่ต้องไล่แก้การ์ดทีละอัน

| บล็อก | ใช้ทำอะไร |
| --- | --- |
| หัวการ์ด | แถบสีด้านบน มีหัวข้อ + บรรทัดรอง (อันแรกกลายเป็น `header` ของ bubble) |
| ตัวเลขเด่น | ตัวเลขใหญ่กลางการ์ด พร้อมหน่วยและหมายเหตุ |
| รายการพร้อมแถบ | หลายแถวจากชุดข้อมูล พร้อมแถบยาวตามสัดส่วน |
| รายการคู่ | หลายแถวแบบ ป้าย … ค่า ไม่มีแถบ |
| ข้อความ | ข้อความอิสระ เลือกโทนปกติ/จาง/เตือน |
| ขึ้นการ์ดใหม่ | ตัดเป็นการ์ดคนละใบ ดูหัวข้อถัดไป |
| เส้นคั่น · ปุ่มลิงก์ | ปุ่มอันสุดท้ายกลายเป็น `footer` ของ bubble |

แต่ละบล็อกที่ดึงหลายแถว**เลือกชุดข้อมูลของตัวเองได้** การ์ดใบเดียวจึงรวมข้อมูล
จากหลาย query ได้ และระบบวิ่ง query ที่ซ้ำกันแค่ครั้งเดียวต่อการส่งหนึ่งครั้ง

แถบยาวเทียบกับ**ค่าสูงสุดในชุดนั้น** ไม่ใช่ค่าคงที่ — วันที่ตัวเลขน้อยทั้งกระดาน
แถบจะยังอ่านออกว่าอันไหนมากกว่ากัน (และ LINE ไม่รับ `width: "0%"` ค่าต่ำสุดจึงเป็น 1%)

บล็อกแบบหลายแถวมีตัวเลือก **"ทำสีแดงเมื่อ"** สามแบบ ป้ายกับตัวเลขจะเป็น `#d02d2d` ตัวหนา
ในข้อความธรรมดาใช้ `⚠` แทนเพราะทำสีไม่ได้

| ตั้งเป็น | ใช้กับ |
| --- | --- |
| แดงเมื่อค่าเป็น 0 | แผนกที่อยากรู้ทันทีว่าวันนี้ไม่มีคนมา เช่นแพทย์แผนไทย |
| แดงเมื่อมากกว่า 0 | งานที่ค้างอยู่ เช่นยังไม่ลง Dx — ศูนย์คือเรื่องดี |

"แดงเมื่อค่าเป็น 0" **ต้องคู่กับ SQL ที่ทำให้แถวมีอยู่เสมอ** ไม่งั้นแถวหายไปตั้งแต่ต้นทาง
ไม่มีอะไรให้ทำแดง ส่วนค่าที่ไม่ใช่ตัวเลข (ข้อความ ค่าว่าง) ไม่เข้าเงื่อนไขทั้งสองแบบ

### เพดาน 10 KB กับบล็อก "ขึ้นการ์ดใหม่"

LINE จำกัด JSON ของข้อความ Flex ไว้ **10 KB ต่อหนึ่งข้อความ ไม่ใช่ต่อคำขอ**
และนับเป็น**ไบต์** ภาษาไทยกินตัวละ 3 ไบต์ใน UTF-8 — วัดด้วย `.length` จะได้ตัวเลข
ต่ำกว่าความจริงเกือบเท่าตัว (การ์ดสรุปวัดได้ 12,511 ตัวอักษร แต่ 13,291 ไบต์)

บล็อก **"ขึ้นการ์ดใหม่"** ตัดตรงนั้นให้เป็นข้อความคนละชิ้น แต่ละชิ้นได้โควตา 10 KB ของตัวเอง
ส่งไปด้วยกันในคำขอเดียว (LINE รับ 5 ข้อความต่อคำขอ เกินกว่านั้นจุดตัดที่เหลือถูกละเลย)
หัวการ์ดของใบแรกถูกยกไปใส่ทุกใบอัตโนมัติ ไม่งั้นการ์ดใบที่สองจะลอยมาโดยไม่มีบริบท
และ altText ติดเลขหน้า `(1/2)` ไม่งั้นในรายการแชทจะดูเหมือนส่งซ้ำ

ข้อความธรรมดาไม่มีเรื่องเพดานนี้ ส่งชิ้นเดียวจบ จุดตัดกลายเป็นเส้นคั่น

ดูขนาดจริงได้ที่ `node ace notify:debug-flex --dump` ซึ่งรายงานเป็นไบต์แยกรายใบ

ทุกการ์ดถูกแปลงเป็นข้อความธรรมดาเก็บคู่กันไว้ในประวัติการส่งด้วย
ประวัติจะได้อ่านรู้เรื่องโดยไม่ต้องเปิด LINE (Flex JSON ดิบยาวเกินกว่าจะมีประโยชน์ในตาราง)

**altText บังคับกรอกสำหรับการ์ด** — เป็นสิ่งที่ LINE แสดงในรายการแชทและใน
notification ก่อนผู้ใช้เปิดการ์ด ถ้าไม่ใส่จะขึ้นแค่คำว่า "ข้อความ"

บล็อกที่ฟอร์มส่งมาถูกคัดทีละฟิลด์ด้วย `parseBlocks()` ไม่ได้รับ object ดิบไปทั้งก้อน
เพราะค่าพวกนี้จะกลายเป็น payload ที่ส่งออกไปหา LINE — ปุ่มลิงก์รับเฉพาะ `http`/`https`
จำกัด 40 บล็อก และตัดความยาวแต่ละช่อง

### ⚠ การ์ด Flex เข้ากลุ่มช้ากว่าข้อความธรรมดามาก

**MOPH Notify ตอบ `200 Succesfully` ตั้งแต่ตอนรับเรื่อง ยังไม่ได้ส่งต่อให้ LINE**
รหัสตอบกลับจึงไม่ได้แปลว่ามีคนเห็นข้อความแล้ว

วัดจริงกับกลุ่ม HAIT WNK เมื่อ 5 ส.ค. 2569

| คำขอมีอะไรอยู่ | เข้ากลุ่ม |
| --- | --- |
| `text` อย่างเดียว | ภายในไม่กี่นาที |
| มี `flex` อยู่ในคำขอ | **ช้าราว 19 นาที** (09:55 → 10:14, 10:08 → 10:27 ห่างเท่ากัน) |

การ์ดไม่ได้หาย แค่คนละคิว — ตอนทดสอบอย่าเพิ่งสรุปว่าไม่เข้าถ้ายังไม่ผ่านไปครึ่งชั่วโมง
**ตั้งรอบส่งเผื่อเวลาไว้ด้วย** อยากให้ถึงมือ 08:00 ควรตั้งไว้ราว 07:40

**ดีเลย์ติดที่คำขอ ไม่ใช่ที่ตัวข้อความ** — ส่ง `text` กับ `flex` รวมใน `messages` ชุดเดียว
(แบบตัวอย่างในคู่มือ) แล้ว `text` จะถูกดองไปพร้อมการ์ดด้วย ถ้าต้องการให้ข้อความด่วน
ถึงทันทีต้องแยกยิงคนละคำขอ

`contents` ต้องเป็น **object** — ลองห่อเป็นสตริง JSON แล้วไม่มีการ์ดโผล่เลย
ทั้งที่ MOPH ยังตอบ `200` เหมือนเดิม

ผลข้างเคียงที่ต้องรู้: ถ้ายิงหลายรอบไล่ ๆ กันเพื่อทดสอบ การ์ดจะทยอยโผล่ทีหลัง
พร้อมกันเป็นพรวด และเรียงไม่ตรงกับลำดับที่ส่ง

**สวิตช์สำรอง** — กลุ่มมี `supports_flex` เผื่อกรณีปลายทางไม่ส่งการ์ดต่อจริง ๆ
ปิดแล้วเทมเพลตแบบการ์ดจะถูกส่งเป็นข้อความธรรมดาแทน (`blocksToPlainText()`
ซึ่งใส่แถบ `█` ให้เทียบสัดส่วนกันเองได้) ข้อมูลครบเหมือนกัน แค่ไม่มีสี
ประวัติการส่งจะระบุไว้ว่ารอบนั้นถอยไปใช้ข้อความธรรมดา — ปกติเปิดไว้

ไล่หาเองได้ด้วย `node ace notify:debug-flex` — `--dump` กาง payload กับข้อความสำรอง
`--probe-group=N` ยิงชุดไล่หาเข้ากลุ่มจริง `--send-group=N` ส่งเทมเพลตจริงผ่านทางเดินปกติ
**ต้องเปิดกลุ่มดูด้วยตาเท่านั้น** และต้องรอนานพอ

| `ptstat` | join `report506status.code` — หาย / ตาย / ยังรักษาอยู่ / ไม่ทราบ |
| `chwpart` `amppart` `tmbpart` | join `thaiaddress` ที่ `codetype = '3'` (ระดับตำบล) |
| `pdx` | ICD-10 ที่วินิจฉัย |

ต่างจากคิวตรงที่เคส 506 คือ**แถวใหม่**จริง ๆ ไม่ใช่การขยับสถานะบนแถวเดิม
จึงตามด้วย watermark ได้ ไม่ต้องสแกนทั้งวันทุกรอบ

รอบแรกที่เปิดใช้งานจะ**ตั้งหลักที่ `MAX(sv_number)` ปัจจุบัน** แล้วแจ้งเฉพาะเคสหลังจากนั้น —
ไม่งั้นจะยิงทะเบียนย้อนหลังหมื่นกว่าเคสเข้ากลุ่มรวดเดียว

ข้อความมีแค่ **ชื่อโรค จำนวน ตำบล/หมู่ แผนก สถานะ** ส่วน HN เป็นตัวเลือกที่ต้องเปิดเอง
(ตั้งต้นปิด) **ชื่อผู้ป่วยกับเลขบัตรไม่ถูกส่งไม่ว่ากรณีใด**

### แจ้งเตือนสถานะระบบให้ทีมงาน

ตั้งที่ `/settings/notify` เตือนได้ 4 เรื่อง เปิด/ปิดแยกกันได้

| เรื่อง | เกิดเมื่อ |
| --- | --- |
| 🔴 poller ทำงานไม่สำเร็จ | `runCycle()` throw เช่นต่อ HOSxP ไม่ได้ |
| 🟢 กลับมาปกติ | รอบก่อนพัง รอบนี้ผ่าน |
| 🟠 ส่งไม่ผ่าน | รอบนั้นมี `failed > 0` — แจ้งเป็นจำนวน ไม่บอกว่าใคร |
| ⚠️ worker กลับมา | ตอน `queue:watch` เริ่มทำงานแล้วพบว่า heartbeat เดิมค้างเกิน 90 วินาที |

เรื่องสุดท้ายอาศัย `restart: unless-stopped` ใน compose — worker ตายแล้ว docker ปลุกขึ้นมาใหม่
ตัวมันเองจะเห็นว่าหายไปนานแล้วรายงานย้อนหลัง **แต่ถ้า worker ตายแล้วไม่ฟื้นเลย
จะไม่มีใครส่งข้อความออกมา** ข้อจำกัดนี้แก้ไม่ได้ด้วยตัวมันเอง ต้องมี monitoring จากข้างนอก

### กติกาที่บังคับไว้ในโค้ด

1. **ห้ามมีข้อมูลผู้ป่วยเข้ากลุ่ม** — `scrubCid()` ใน
   [notify_client.ts](app/services/notify_client.ts) ตัดเลข 13 หลักทิ้งที่ชั้นล่างสุด
   ก่อนส่งทุกครั้ง ไม่ต้องไว้ใจว่าทุกจุดที่เรียกใช้ระวังครบ
   การ์ด Flex ใช้ `scrubDeep()` เดินทุกค่าที่เป็นสตริงในก้อน แทนการ stringify
   ทั้งก้อนแล้วแทนที่ (ซึ่งจะทำให้ตัวเลข 13 หลักที่เป็น number literal พัง JSON)
2. **ห้ามทำให้ poller ล้ม** — ส่งแจ้งเตือนไม่ได้ก็แค่ log ทิ้ง งานหลักต้องเดินต่อ
3. **ห้ามสแปม** — throttle รายเรื่อง นับเวลาเฉพาะตอนส่งสำเร็จ
   (ส่งไม่ออกแล้วนับว่าเตือนแล้วคือหลอกตัวเอง)
4. **ประวัติเก็บข้อความตามที่ส่งจริง** ไม่ใช่เทมเพลต — เทมเพลตแก้ทีหลังได้
   แต่ประวัติต้องตอบได้ว่าตอนนั้นส่งอะไรออกไป
5. **ประวัติการแก้ไขไม่ใช่ที่เก็บ secret** — ช่องที่ชื่อมี key/secret/password/token
   ถูกแทนด้วย `•••` ก่อนบันทึก

### ปุ่มทดสอบ

**ทดสอบ key** ยิงคำขอที่ไม่มี `messages` — `require messages` = key ถูก,
`Unauthorized` = key ผิด ไม่มีอะไรโผล่ในกลุ่มทั้งสองกรณี
ส่วน **ส่งข้อความทดสอบเข้ากลุ่ม** ส่งจริง มี confirm ก่อน

ขั้นตอนฝั่ง MOPH: สร้างกลุ่ม LINE ชื่อลงท้าย `HC` + hoscode 5 หลัก → เชิญ “LINE หมอพร้อม”
เข้ากลุ่ม → admin หน่วยบริการอนุมัติใน CMS เมนู “กลุ่มบอท” → คัดลอก Client_ID / Secret

## Poller

อ่านจาก `ovst_queue_server` ทุก 15 วินาที รายละเอียดกลไกอยู่ที่
[docs/queue-detection.md](docs/queue-detection.md)

```bash
docker compose run --rm web node ace queue:watch --once
```

รันรอบเดียวแล้วออก ใช้ตอนทดสอบ ส่วนใน compose ตัว `worker` รันวนไปเรื่อย ๆ

**กันส่งซ้ำ** ด้วย `notifications.dedup_key UNIQUE` + `ON CONFLICT DO NOTHING`
ที่ระดับฐานข้อมูล ไม่ใช่เช็คก่อนแล้วค่อย insert เพราะสองรอบที่ซ้อนกันจะเช็คผ่านทั้งคู่

**ไม่เก็บเลขบัตรประชาชนในฐานเรา** — `notifications.payload` ไม่มี `cid`
ตอนจะส่งจริงค่อยอ่านสด ๆ จาก `patient` ด้วย `hn` แล้ว log แบบปิดบัง

**ไม่ใช้ `wait_dep`** เพราะยังยืนยันความหมายไม่ได้ นับจำนวนคิวที่รอเองจากตำแหน่ง
ในห้องเดียวกันเรียงตาม `time_visit`

### เครื่องมือสำรวจ

```bash
docker compose run --rm web node ace hosxp:discover
```

```bash
docker compose run --rm web node ace hosxp:probe-queue
```

## สถานะ

ทำเสร็จแล้ว: หน้าตั้งค่าทั้งหมด · จัดการผู้ใช้ · หน้าสถานะ + heartbeat ·
ออกแบบข้อความ · ทดสอบส่งรายเคส · **poller ตรวจจับและส่งครบวงจร** ·
บันทึกการส่ง + retry · dry run · ช่วงเวลางดส่ง · เปิด/ปิดรายห้อง ·
**ระบบ MOPH Notify ครบ 8 หน้า** (ภาพรวม · ตารางเวลา · CDCU · เทมเพลต · ชุดข้อมูล ·
กลุ่ม LINE · ประวัติการส่ง · ประวัติการแก้ไข) · **เทียบเครื่องฐานข้อมูลสามเครื่อง**

### ยังต้องยืนยันก่อนปิด dry run

1. **`status` ของ `ovst_queue_server`** — ตอนนี้ส่งเฉพาะ `status = 1`
   ถ้าค่านี้ไม่เปลี่ยนหลังตรวจเสร็จ ระบบจะแจ้งเตือนคนที่กลับบ้านไปแล้ว
2. **ห้องที่เปิด** — ตั้งต้นปิดหมด เปิดทีละห้องแล้วดูใน `/log` ก่อน
3. **เลขคิวที่คนไข้เห็น** — ระบบใช้ `depq` (`A123`) ตรวจกับบัตรคิวจริงว่าตรงกัน

### ยังไม่ได้ทำ

- ลบ `visit_states` ของวันเก่าอัตโนมัติ (ตอนนี้สะสมไปเรื่อย ๆ)
- retention policy ของ `notifications` ตาม PDPA
- circuit breaker เมื่อ MOPH ล่มยาว (ตอนนี้แค่ retry 3 ครั้งต่อรายการ)
- **ตัวตาม `.212` และ `.203` ยัง `read_only = OFF`** — เขียนลงตรง ๆ ได้ทั้งคู่
  ถ้าไม่ได้ตั้งใจ ควรให้ DBA เปิด `read_only` เพื่อปิดทางที่ข้อมูลจะแยกกัน
