# คู่มือติดตั้ง

สำหรับเจ้าหน้าที่ไอทีโรงพยาบาลที่จะนำระบบไปติดตั้ง ไม่ต้องเขียนโปรแกรมเป็น
แต่ต้องเข้าถึงฐานข้อมูล HOSxP และติดต่อ admin หน่วยบริการของหมอพร้อมได้

อ่าน [README](../README.md) ถ้าอยากรู้ว่าระบบทำงานยังไงและตัดสินใจอะไรไว้เพราะอะไร

---

## 1. ของที่ต้องขอล่วงหน้า

**เริ่มขอตั้งแต่วันนี้** สามข้อแรกต้องรอคนอื่นอนุมัติ ใช้เวลาเป็นวันถึงสัปดาห์
ส่วนการติดตั้งจริงใช้เวลาไม่ถึงชั่วโมง

| # | สิ่งที่ต้องมี | ขอจากใคร | ถ้าไม่มีจะเป็นยังไง |
| --- | --- | --- | --- |
| 1 | **client-key / secret-key ของ MOPH Alert** | admin หน่วยบริการ ใน CMS MOPH ALERTING เมนู “จัดการ Token” | ส่งหาผู้ป่วยไม่ได้เลย |
| 2 | **โลโก้โรงพยาบาลใน CMS** | admin หน่วยบริการ อัปโหลดในระบบ | key ถูกแต่**ส่งจริงไม่ผ่าน** ดูข้อ 7 |
| 3 | **กลุ่ม LINE + key ของ MOPH Notify** | ดูขั้นตอนด้านล่าง | แจ้งเตือนเจ้าหน้าที่และ CDCU ใช้ไม่ได้ |
| 4 | **user อ่านอย่างเดียวบนฐาน HOSxP** | DBA หรือผู้ดูแล HOSxP | ระบบไม่มีข้อมูลจะอ่าน |
| 5 | **เครื่องสำหรับรัน + เส้นทางเครือข่ายถึงฐาน HOSxP** | ทีมไอทีเอง | — |

### ขั้นตอนขอกลุ่ม LINE (ข้อ 3)

1. สร้างกลุ่ม LINE ตั้งชื่อ**ลงท้ายด้วย `HC` ตามด้วย hoscode 5 หลัก**
2. เชิญบัญชี **“LINE หมอพร้อม”** เข้ากลุ่ม
3. ให้ admin หน่วยบริการอนุมัติใน CMS เมนู **“กลุ่มบอท”**
4. คัดลอก **Client_ID / Secret** ของกลุ่มนั้นมาใช้

ทำซ้ำได้หลายกลุ่ม เช่นแยกกลุ่มทีมไอทีกับกลุ่ม SRRT

### user อ่านอย่างเดียว (ข้อ 4)

รันบนเครื่องฐานข้อมูลของโรงพยาบาล **ไม่ใช่ในคอนเทนเนอร์**

```sql
CREATE USER 'queuewnk_ro'@'%' IDENTIFIED BY 'ตั้งรหัสเอง';
GRANT SELECT ON hos.* TO 'queuewnk_ro'@'%';
FLUSH PRIVILEGES;
```

> **ให้สิทธิ์แค่ `SELECT` เท่านั้น** ระบบปฏิเสธคำสั่งที่ไม่ใช่การอ่านตั้งแต่ในโค้ดอยู่แล้ว
> แต่สิทธิ์ระดับ MySQL เป็นด่านที่สองที่ไม่ควรข้าม ถ้า DBA ให้สิทธิ์เขียนมาด้วย
> หน้าทดสอบการเชื่อมต่อจะขึ้นคำเตือนให้

แคบ `@'%'` ลงเป็น subnet ของเครื่องที่รันระบบได้ยิ่งดี — **ต้องเป็น IP ที่คอนเทนเนอร์
ออกไป ไม่ใช่ IP ของเครื่องโฮสต์** ปุ่มทดสอบในหน้า `/settings/hosxp` จะบอก IP นั้น
มาให้ในข้อความ error ถ้าต่อไม่ได้

### เครื่องที่ใช้รัน (ข้อ 5)

| | |
| --- | --- |
| ระบบปฏิบัติการ | อะไรก็ได้ที่ลง Docker ได้ — Linux, Windows Server, Windows 11 |
| CPU | 2 คอร์พอ |
| RAM | **ขั้นต่ำ 2 GB · แนะนำ 4 GB** |
| ดิสก์ | 20 GB พอสำหรับหลายปี |
| เครือข่าย | ต้องต่อถึงฐาน HOSxP **และออกไปถึง `*.moph.go.th` ได้** |

> **เครื่องต้องออกไปถึง `*.moph.go.th` ได้เสมอ** การส่งข้อความถึงผู้ป่วยและเข้ากลุ่ม LINE
> วิ่งผ่าน API ของกระทรวงทั้งหมด ถ้าออกไปไม่ได้ ระบบนี้ใช้ไม่ได้ — แต่**ไม่ต้องออกไป
> ที่อื่นเลย** ตัวติดตั้งไม่ดึงอะไรจากอินเทอร์เน็ต เพราะ image มาจากไฟล์ที่แจกให้

วัดจากเครื่องที่ใช้งานจริง ทั้งสี่คอนเทนเนอร์รวมกันใช้ RAM ประมาณ **730 MB**
(ตัวเลขนี้วัดจากโหมดพัฒนา ตอนติดตั้งจริงจะกินน้อยกว่านี้)
ฐานข้อมูลของแอปโตประมาณ **8 MB ต่อสองสามสัปดาห์** ที่ปริมาณผู้ป่วย ~200 คน/วัน
คิดเป็นไม่ถึง 1 GB ต่อปี ดิสก์ไม่ใช่เรื่องที่ต้องห่วง

**ต้องเปิดเครื่องทิ้งไว้ตลอด** ระบบเฝ้าคิวทุก 15 วินาที เครื่องปิดคือไม่มีการแจ้งเตือน

## 2. ติดตั้ง

ต้องมี **Docker** อย่างเดียว ไม่ต้องลง Node ไม่ต้องลง MariaDB และ**ไม่ต้องมีซอร์สโค้ด**

**ของที่ต้องมี 3 ไฟล์** อยู่โฟลเดอร์เดียวกัน

| ไฟล์ | คืออะไร | ขนาด |
| --- | --- | --- |
| `queuewnk-v0.1.0-images.tar.gz` | ตัวระบบ **และ MariaDB** รวมอยู่ในไฟล์เดียว | ~181 MB |
| `compose.prod.yml` | ตัวกำหนดว่าจะรันอะไรบ้าง | เล็ก |
| `.env.example` | แบบฟอร์มค่าตั้งค่า | เล็ก |

> **MariaDB รวมมาให้แล้วในไฟล์เดียวกัน** ไม่ต้องติดตั้งฐานข้อมูลเองและไม่ต้องดาวน์โหลดเพิ่ม

### 2.1 โหลด image เข้า Docker

```bash
docker load -i queuewnk-v0.1.0-images.tar.gz
```

ต้องขึ้นสองบรรทัด ถ้าขึ้นบรรทัดเดียวแปลว่าไฟล์ไม่ครบ

```
Loaded image: queuewnk:0.1.0
Loaded image: mariadb:12
```

### 2.2 เตรียมค่าตั้งค่า

**มีแค่ 2 บรรทัดที่ต้องกรอก ที่เหลือปล่อยไว้ทั้งหมด** แต่**ต้องทำตามลำดับนี้**

```bash
cp .env.example .env
```

**ก) เปิด `.env` ด้วย Notepad หรืออะไรก็ได้ แล้วกรอก `DB_PASSWORD=` ก่อน**

ตั้งเองอะไรก็ได้ เป็นรหัสของฐานข้อมูลที่ระบบสร้างขึ้นมาเอง ไม่ต้องจำและไม่ได้ใช้ที่อื่น
**ไม่ใช่**รหัสของ HOSxP — ตัวนั้นกรอกผ่านหน้าเว็บทีหลังในขั้นที่ 3

> ต้องกรอกบรรทัดนี้ก่อน ไม่งั้นคำสั่งในข้อ ข) จะขึ้นว่า
> `required variable DB_PASSWORD is missing a value` แล้วไม่ทำอะไรให้
> เพราะ Docker อ่านไฟล์ตั้งค่าทั้งไฟล์ก่อนจะเริ่มทำงาน

**ข) สร้างกุญแจ**

```bash
docker compose -f compose.prod.yml run --rm --no-deps web node ace generate:key
```

พิมพ์ค่ายาว ๆ ออกมาบรรทัดหนึ่ง หน้าตาแบบ `APP_KEY = kFwKPhvbW9us7RZp...`

**ค) เอาค่านั้นไปใส่ `APP_KEY=` ใน `.env`** เอาเฉพาะค่า ไม่เอาคำว่า `APP_KEY =` ข้างหน้า

ระบบจะไม่ยอมสตาร์ตถ้าเว้นบรรทัดใดบรรทัดหนึ่งไว้ จึงไม่มีทางลืมโดยไม่รู้ตัว

### 2.3 เปิดระบบ

```bash
docker compose -f compose.prod.yml up -d
```

```bash
docker compose -f compose.prod.yml exec web node ace migration:run --force
```

```bash
docker compose -f compose.prod.yml exec web node ace admin:create you@hospital.go.th 'รหัสผ่านอย่างน้อย8ตัว' 'ชื่อ นามสกุล'
```

เปิด `http://<ไอพีเครื่อง>:3333` แล้วล็อกอินด้วยบัญชีที่เพิ่งสร้าง

ถ้าเปิดไม่ขึ้น ดูว่ามีอะไรใช้พอร์ต 3333 อยู่หรือเปล่า เปลี่ยนได้ที่ `WEB_PORT` ใน `.env`

### 2.4 อัปเดตเป็นรุ่นใหม่

```bash
docker load -i queuewnk-v0.1.1-images.tar.gz
```

แก้ `QUEUEWNK_IMAGE` ใน `.env` ให้เป็นเลขรุ่นใหม่ (ถ้ายังไม่มีบรรทัดนี้ให้เพิ่มเข้าไป) แล้ว

```bash
docker compose -f compose.prod.yml up -d
```

```bash
docker compose -f compose.prod.yml exec web node ace migration:run --force
```

**ไม่มีขั้นตอน restart ให้ลืม** เพราะ `up -d` สร้าง container ใหม่จาก image ใหม่ให้เอง
`.env` และฐานข้อมูลไม่ถูกแตะ ค่าที่ตั้งไว้ในหน้าเว็บอยู่ครบ

**image รุ่นเก่ายังค้างอยู่ในเครื่อง** ย้อนกลับได้ทันทีถ้ารุ่นใหม่มีปัญหา แค่แก้เลขรุ่นใน `.env`
กลับแล้ว `up -d` ใหม่ — แต่ถ้ารุ่นใหม่มี migration ที่เปลี่ยนโครงฐาน **การย้อน image
ไม่ได้ย้อนฐานให้ด้วย** อ่าน [CHANGELOG](../CHANGELOG.md) ก่อนอัปเดตเสมอ

ลบรุ่นเก่าด้วย `docker rmi queuewnk:0.1.0` เมื่อมั่นใจแล้วว่ารุ่นใหม่ใช้ได้

### เรื่อง APP_KEY ที่ต้องอ่านให้จบ

`APP_KEY` คือกุญแจที่ใช้เข้ารหัสรหัสผ่าน HOSxP และ secret ของ MOPH ก่อนเก็บลงฐาน

| ข้อห้าม | ถ้าฝ่าฝืน |
| --- | --- |
| **ห้ามเปลี่ยนหลังตั้งแล้ว** | ค่าที่เข้ารหัสไว้เดิมถอดไม่ออก ต้องไปกรอกรหัสผ่านใหม่ทุกหน้า |
| **ห้ามใช้ค่าเดียวกับโรงพยาบาลอื่น** | ใครที่มีไฟล์สำรองของคุณจะถอดรหัสได้ |
| **ต้องสำรองเก็บไว้คู่กับ backup ฐานข้อมูล** | restore ฐานกลับมาแล้วใช้ไม่ได้ ข้อมูลที่เข้ารหัสไว้กลายเป็นขยะ |

เก็บไว้ในที่เดียวกับที่เก็บรหัสผ่านสำคัญอื่นของโรงพยาบาล ไม่ใช่ในไฟล์ที่แชร์กันในกลุ่มไลน์

### ถ้าต้องแก้โค้ด

ระบบอ่านคิวจากตาราง `ovst_queue_server` แบบตายตัว **โรงพยาบาลที่ไม่ได้ใช้ HOSxP
Queue Server ต้องแก้ SQL เอง** ซึ่งทำใน image ไม่ได้ ต้องติดตั้งจากซอร์สแทน

ยังไม่รู้ว่าใช้อยู่หรือเปล่าก็ติดตั้งตามข้างบนไปก่อน แล้วไปดูขั้นที่ 4 —
ย้ายทีหลังได้โดยไม่เสียข้อมูล เพราะฐานข้อมูลอยู่ใน volume แยกจาก image

ขั้นตอนติดตั้งจากซอร์สอยู่ใน [README](../README.md#ติดตั้งจากซอร์ส-สำหรับคนที่จะแก้โค้ด)

## 3. ตั้งค่าผ่านหน้าเว็บ

เปิด `http://<ไอพีเครื่อง>:3333` แล้วล็อกอินด้วยบัญชีที่สร้างจาก `admin:create`

ทำตามลำดับนี้ อย่าข้าม

| ลำดับ | หน้า | ทำอะไร | ตรวจว่าสำเร็จยังไง |
| --- | --- | --- | --- |
| 1 | `/settings/hosxp` | กรอก host / port / database / user / รหัส / charset | กด **ทดสอบการเชื่อมต่อ** แล้ว**ต้องเห็นชื่อผู้ป่วยภาษาไทยอ่านออก** |
| 2 | `/settings/moph` | กรอก Base URL / client-key / secret-key | กด **ทดสอบ key** — ดูตารางแปลผลในข้อ 7 |
| 3 | `/notify/groups` | เพิ่มกลุ่ม LINE พร้อม Client_ID / Secret | กด **ทดสอบการเชื่อมต่อ** แล้วดูว่ามีข้อความเข้ากลุ่มจริง |
| 4 | `/settings/templates` | ออกแบบข้อความแจ้งเตือนทั้ง 4 เคส | ดูตัวอย่างในหน้า |
| 5 | `/settings/poller` | **ยังไม่ต้องแตะ** ค่าตั้งต้นคือ dry run เปิด ปิดทุกห้อง | — |

**ขั้นที่ 1 สำคัญที่สุด** ถ้าชื่อผู้ป่วยขึ้นเป็นตัวขยะแล้วปล่อยผ่าน ชื่อขยะนั้นจะถูกส่งเข้า
หมอพร้อมถึงมือผู้ป่วยจริง HOSxP v3 มักต้องใช้ `tis620` ลองเปลี่ยน charset แล้วกดทดสอบ
ใหม่ได้เรื่อย ๆ เพราะปุ่มทดสอบใช้ค่าที่กำลังกรอกอยู่ ยังไม่บันทึก

## 4. สำรวจฐานของโรงพยาบาลตัวเองก่อน — ห้ามข้าม

ระบบนี้พัฒนากับ HOSxP ของโรงพยาบาลเดียว **สิ่งที่จริงที่นั่นอาจไม่จริงที่คุณ**

```bash
docker compose -f compose.prod.yml exec web node ace hosxp:discover
```

```bash
docker compose -f compose.prod.yml exec web node ace hosxp:probe-queue
```

(ติดตั้งแบบ ข ให้ตัด `-f compose.prod.yml` ออก)

สี่อย่างที่ต้องดูให้ออก

| ตรวจอะไร | ผลที่ควรได้ | ถ้าไม่เป็นอย่างนั้น |
| --- | --- | --- |
| **ตารางคิวไหนมีข้อมูล** | `ovst_queue_server` มีแถวของวันนี้ | ถ้าว่างแต่ `opd_queue` มีข้อมูล **ต้องแก้ SQL ใน `app/services/queue_poller.ts` เอง** (ต้องติดตั้งแบบ ข) |
| **ภาษาไทยอ่านออกไหม** | ชื่อผู้ป่วยอ่านรู้เรื่อง | เปลี่ยน charset ในหน้า `/settings/hosxp` |
| **นาฬิกาต่างกันกี่วินาที** | ไม่เกิน 60 วินาที | ตั้งเวลาเครื่องให้ตรงกัน ไม่งั้นการตรวจจับด้วยเวลาจะพลาด |
| **`cid` ครบ 13 หลักกี่ %** | ยิ่งใกล้ 100% ยิ่งดี | ผู้ป่วยที่ไม่มีเลขบัตรจะไม่ได้รับข้อความ ไม่ใช่บั๊ก |

> เรื่อง `cid` มีกับดัก — ถ้าสุ่มจากตาราง `patient` เฉย ๆ จะได้ตัวเลขต่ำเกินจริง
> เพราะได้ทะเบียนเก่าที่ยังไม่บังคับกรอกเลขบัตรมา ตัวเลขที่ใช้ตัดสินใจได้คือของ
> **คนที่เดินเข้ามารับบริการจริง** ซึ่งเครื่องมือสำรวจคำนวณให้แล้ว

## 5. เปิดใช้จริง — ทีละขั้น อย่ารีบ

ห้ามเปิดทุกห้องพร้อมกันในวันแรก ผู้ป่วยได้รับข้อความผิดแล้วเรียกคืนไม่ได้

**ขั้นที่ 1 — dry run ทั้งวัน**
เปิดห้องที่คนน้อยที่สุดหนึ่งห้อง โดย**ยังเปิด dry run ไว้** ระบบจะบันทึกว่า
“ตั้งใจจะส่งอะไรบ้าง” ลงหน้า `/log` โดยไม่ส่งออกไปจริง ปล่อยไว้ทั้งวัน

**ขั้นที่ 2 — ตรวจ log กับบัตรคิวจริง**
เอาเลขคิวใน `/log` ไปเทียบกับบัตรคิวที่ผู้ป่วยถืออยู่ **ต้องตรงกัน**
ถ้าไม่ตรงแปลว่าอ่านคอลัมน์ผิด อย่าเพิ่งไปต่อ

**ขั้นที่ 3 — ทดสอบส่งด้วยเลขบัตรของตัวเอง**
หน้า `/test` เลือกเคส กรอกข้อมูลสมมติ ดู payload แล้วส่งจริง
**ใช้เลขบัตรของตัวเองหรือของเจ้าหน้าที่ที่ยินยอมแล้วเท่านั้น** ข้อความจะไปถึง
LINE หมอพร้อมของเจ้าของเลขนั้นจริง

**ขั้นที่ 4 — ปิด dry run ห้องเดียว**
เปิดจริงห้องเดียวก่อน เฝ้าดูหน้า `/log` และรับฟังจากหน้างานหนึ่งถึงสองวัน

**ขั้นที่ 5 — ขยายทีละห้อง**
เพิ่มทีละห้อง ดูผลก่อนเพิ่มห้องถัดไป

## 7. ปัญหาที่เจอบ่อย

### ตอนกดทดสอบ key ของ MOPH Alert

ปลายทางตรวจ key ก่อนตรวจเลขบัตรเสมอ จึงทดสอบได้โดยไม่มีข้อความถึงผู้ป่วยจริง

| ข้อความที่ได้ | แปลว่า | ทำยังไง |
| --- | --- | --- |
| `404 Error template` | **key ถูกต้อง** (แค่หาเลขบัตรสมมติไม่เจอ ตามคาด) | ผ่านแล้ว ไปต่อได้ |
| `401 client-key or secret-key incorrect` | key ผิด | คัดลอกใหม่จาก CMS ระวังช่องว่างติดมา |
| `401 Hospital Logo is empty` | **key ถูก แต่ยังไม่ได้อัปโหลดโลโก้ใน CMS** | ให้ admin หน่วยบริการอัปโหลด ไม่งั้นส่งจริงไม่ผ่าน |

### ตอนต่อฐาน HOSxP

| อาการ | สาเหตุที่พบบ่อย |
| --- | --- |
| ต่อไม่ได้เลย ทั้งที่รหัสถูก | `GRANT` ผูกกับ IP ผิด — ต้องเป็น**ไอพีที่คอนเทนเนอร์ออกไป** ไม่ใช่ไอพีเครื่องโฮสต์ ข้อความ error จะบอกไอพีนั้นมาให้ |
| **ชื่อผู้ป่วยเป็นตัวขยะ** | charset ผิด ลอง `tis620` |
| ชื่อขยะแบบ `เธ‡เธ˜` | แปลง charset ซ้ำสองชั้น ถ้าเขียน SQL เองอยู่ **อย่าใส่ `CONVERT`** ระบบต่อด้วย `TIS620_THAI_CI` อยู่แล้ว |
| ขึ้นเตือนว่าเวลาต่างกันเกิน 60 วินาที | นาฬิกาเครื่องไม่ตรง แก้ก่อนใช้งาน |

### ตอนใช้งาน

| อาการ | สาเหตุ | ทางแก้ |
| --- | --- | --- |
| **ไม่มีคิวขึ้นใน `/log` เลย** | ยังไม่ได้เปิดห้อง หรือตารางคิวไม่ตรง | เช็ก `/settings/poller` ว่าเปิดห้องไว้ไหม แล้วรัน `hosxp:probe-queue` |
| คอนเทนเนอร์ไม่ยอมสตาร์ต | `.env` ขาดตัวแปร | ระบบจะบอกชื่อตัวที่ขาด เทียบกับ `.env.example` ให้ครบ |
| **จู่ ๆ ต้องกรอกรหัสผ่านใหม่ทุกหน้า** | `APP_KEY` เปลี่ยนไป | เอาค่าเดิมกลับมา ถ้าหายต้องกรอกใหม่ทุกหน้าจริง ๆ |
| **ล็อกอินแล้วเด้งกลับหน้าล็อกอินวนไป** ไม่มีข้อความว่าผิดตรงไหน | ตั้ง `COOKIE_SECURE=true` แต่เข้าผ่าน `http://` เบราว์เซอร์จึงไม่ส่ง cookie กลับ | ตั้งเป็น `false` ใน `.env` แล้ว `restart web` — ดูกล่องข้างล่าง |
| **การ์ดสรุปไม่เข้ากลุ่ม LINE** | ปลายทางดองการ์ดไว้ **ราว 19 นาที** | ไม่ใช่บั๊ก รอให้ครบครึ่งชั่วโมงก่อนสรุปว่าไม่เข้า ตั้งรอบส่งเผื่อเวลาไว้ |
| ข้อความธรรมดาเข้าเร็ว แต่การ์ดช้า | ดีเลย์ติดที่คำขอที่มีการ์ดปนอยู่ | เรื่องปกติของปลายทาง |
| **แก้โค้ดแล้วหน้าเว็บไม่เปลี่ยน** (แบบ ข) | โค้ดใหม่ยังไม่ถูกโหลด | `docker compose restart web worker notify` — ดูกล่องข้างล่าง |
| ผู้ป่วยบางคนไม่ได้รับข้อความ | ไม่มีเลขบัตรในทะเบียน หรือยังไม่ผูก LINE หมอพร้อม | ตรวจจาก `/log` ว่าระบบพยายามส่งหรือเปล่า |

> **เรื่อง `COOKIE_SECURE`** — ค่าตั้งต้นคือ `false` เพราะโรงพยาบาลส่วนใหญ่เปิดหน้านี้
> ผ่าน `http://<ไอพี>:3333` บนวงแลนภายใน **ตั้งเป็น `true` ต่อเมื่อมี HTTPS อยู่หน้าระบบแล้ว
> เท่านั้น** ตั้ง `true` ทั้งที่ยังเป็น http จะล็อกอินไม่ได้เลยและไม่มีข้อความบอกสาเหตุ
>
> ถ้าระบบนี้ต้องเข้าถึงจากนอกวงแลนโรงพยาบาล **ควรมี HTTPS คั่นหน้าจริง ๆ**
> แล้วค่อยเปิด `COOKIE_SECURE=true` เพราะรหัสผ่านผู้ดูแลวิ่งผ่านสายแบบไม่เข้ารหัส
> ถ้าใช้งานอยู่แต่ในวงแลนตามปกติ ปล่อย `false` ไว้ได้

> **กับดักที่เสียเวลาที่สุดของการติดตั้งแบบ ข** — โค้ดถูก mount เข้าคอนเทนเนอร์
> และบน Windows สัญญาณไฟล์เปลี่ยนไม่ทะลุเข้าไป ตัวรีโหลดอัตโนมัติจึงไม่ทำงาน
> ที่หลอกกว่านั้นคือไฟล์หน้าเว็บ (`.edge`) ถูกอ่านใหม่ทุกคำขออยู่แล้ว
> **หน้าเว็บจึงดูเหมือนอัปเดตแล้ว ทั้งที่โค้ดเบื้องหลังยังเป็นตัวเก่า**
> กด “บันทึก” แล้วค่ากลับมาเป็นเดิมคืออาการคลาสสิกของเรื่องนี้ — สั่ง `restart` แล้วหาย

## 8. เรื่องที่ต้องระวังเป็นพิเศษ

**เลขบัตรประชาชน** ระบบไม่เก็บลงฐานของแอปและตัดทิ้งก่อนส่งเข้ากลุ่ม LINE ทุกครั้ง
**อย่าแก้พฤติกรรมนี้** และอย่าเอาเลขบัตรไปใส่ในชุดข้อมูลที่เขียน SQL เอง

**ข้อมูลผู้ป่วยในกลุ่ม LINE** หน้า CDCU เปิดให้ส่งชื่อ HN เบอร์โทรเข้ากลุ่มได้
ตั้งต้นปิดทั้งหมด **เปิดเมื่อจำเป็นและเข้าใจว่ากลุ่มแชทมีคนอ่านหลายคน**
คนที่ออกจากทีมไปแล้วอาจยังอยู่ในกลุ่ม ควรทบทวนสมาชิกกลุ่มก่อนเปิด

**ห้ามสร้างเคส 506 ปลอมในฐาน HOSxP เพื่อทดสอบ** ใช้ `cdcu:check --demo` แทน

**ระบบไม่เขียนอะไรลงฐาน HOSxP เลย** ถ้ามีใครเสนอให้เพิ่ม trigger หรือสร้างตาราง
ในฐานโรงพยาบาลเพื่อให้ระบบทำงานง่ายขึ้น — นั่นผิดหลักการที่ระบบนี้ยึดไว้
และเป็นเหตุผลที่มันได้รับอนุญาตให้ต่อกับฐานจริงตั้งแต่แรก
