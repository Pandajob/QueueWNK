# การตรวจจับเหตุการณ์คิว

บันทึกจากการสำรวจฐานจริง 3 ส.ค. 2569 — รันซ้ำได้ด้วย

```bash
docker compose run --rm web node ace hosxp:probe-queue
```

## แหล่งข้อมูล: `ovst_queue_server`

ไม่ใช่ `opd_queue` — ตารางนั้นชื่อตรงที่สุดแต่**ว่างเปล่า** (0 แถววันนี้)
โรงพยาบาลนี้ใช้ Queue Server ของ HOSxP

| ฟิลด์ | ใช้ทำอะไร | ตัวอย่าง |
| --- | --- | --- |
| `vn` | คีย์หลัก และเป็น timestamp ในตัว (`690803134422` = 69-08-03 13:44:22) | |
| `depq` | **เลขคิวที่คนไข้เห็น** | `A123` `I005` `H011` `N001` |
| `dep` | ห้องที่อยู่ตอนนี้ เปลี่ยนเมื่อย้าย | `037` |
| `opd_dep` | ห้องแรกที่เข้า ไม่เปลี่ยน | `010` |
| `time_visit` | **เวลาที่เข้าห้องปัจจุบัน — ขยับทุกครั้งที่ย้าย** | `13:43:08` |
| `time_visit_opd` | เวลาลงทะเบียนครั้งแรก ไม่เปลี่ยน | `13:25:07` |
| `hn` | ใช้ join ไป `patient.cid` | |
| `fullname` | ชื่อคนไข้ ไม่ต้อง join เพิ่ม | |
| `status` | สถานะ — พบค่า 1 (158 แถว) และ 2 (4 แถว) | |
| `wait_dep` | ยังไม่ยืนยันความหมาย | `9` `70` `NULL` |

ชื่อห้องมาจาก `kskdepartment.department` โดย join ด้วย `depcode`

## ตัวเลขที่สำรวจได้

```
rows_today=162  distinct_vn=162  departments=11  has_depq=162
first_at=07:14:34  last_at=13:44:22
rows_per_vn=1  visits=162
```

**หนึ่ง visit ได้หนึ่งแถวเสมอ** ต่อให้ PK เป็น `(vn, opdq)` แบบคู่ ค่า `opdq` ก็ไม่เปลี่ยนระหว่างวัน
แปลว่าการย้ายห้องเป็นการ **UPDATE ทับแถวเดิม** ไม่ใช่ INSERT แถวใหม่

วันนี้ `ovst` มี 273 visit แต่ `ovst_queue_server` มี 162 — ไม่ใช่ทุก visit ที่ผ่านระบบคิว
(ER, ตึกผู้ป่วยใน, ทันตกรรม อาจไม่ผ่าน) ซึ่งถูกต้องแล้ว เพราะเราควรแจ้งเฉพาะคนที่มีคิวจริง

## กลไกที่ใช้ตรวจจับ

`time_visit` ขยับทุกครั้งที่คนไข้ย้ายห้อง จึงใช้เป็น watermark ได้โดยตรง
ไม่ต้องกวาดทั้งตารางทุกรอบ

```sql
SELECT vn, hn, fullname, depq, dep, opd_dep, status, wait_dep,
       time_visit, time_visit_opd
  FROM ovst_queue_server
 WHERE date_visit = CURDATE()
   AND time_visit > ?      -- watermark จากรอบก่อน
 ORDER BY time_visit
```

แต่ watermark บอกได้แค่ว่า "แถวนี้เปลี่ยน" ไม่ได้บอกว่า**เปลี่ยนอะไร**
จึงยังต้องมีตาราง `visit_states` ฝั่งเราเก็บ snapshot ล่าสุดต่อ `vn`
(`dep`, `depq`, ส่งอะไรไปแล้วบ้าง) ไว้เทียบ เพราะ HOSxP ไม่เก็บประวัติการย้าย
และเราเขียนอะไรลงฐานเขาไม่ได้

| เหตุการณ์ | เงื่อนไข |
| --- | --- |
| แจ้งเตือนคิว | เจอ `vn` ที่ยังไม่มีใน `visit_states` |
| คิวเปลี่ยน | `dep` หรือ `depq` ต่างจาก snapshot |
| ใกล้ถึงคิว | จำนวนคนที่รออยู่ข้างหน้าในห้องเดียวกัน ≤ threshold |
| จบแล้ว | `dep = '999'` (กลับบ้าน) → เลิกส่ง |

### ข้อจำกัดที่ยอมรับ

poll ทุก 15 วินาที ถ้าคนไข้ถูกย้ายสองห้องภายในช่วงนั้น จะเห็นแค่ห้องปลายทาง
ขั้นกลางหายไป ในทางปฏิบัติไม่กระทบ แต่ควรรู้ไว้

## ต่อเครื่องหลักหรือ replica

วัดจากของจริงด้วย `node ace hosxp:server-info`

คำสั่งนี้คืน `hostname` · `read_only` · `server_id` · `log_bin` ของเครื่องที่ต่ออยู่

อ่านผลแบบนี้ — `read_only = OFF` แปลว่าเครื่องนั้นรับการเขียน ส่วน `server_id` ที่ไม่ใช่ค่า
ตั้งต้นคู่กับ `log_bin = ON` บอกว่ามีระบบ replication อยู่ในบ้าน แต่บอกไม่ได้ว่าเครื่องไหน
เป็นต้นทางเครื่องไหนเป็นตัวตาม เพราะ user ที่มีแค่ `SELECT` อ่าน `SHOW SLAVE STATUS`
ไม่ได้ (ต้องมีสิทธิ์ `REPLICATION CLIENT` ซึ่งเราตั้งใจไม่ขอ) ตรงนี้ต้องถาม DBA ของ
โรงพยาบาลเอาเอง หรือดูวิธีเดาจาก GTID ในหัวข้อ `/settings/db-sync` ของ README

**ชี้ poller ไปที่เครื่องที่สดที่สุดเท่าที่ยอมรับได้** ไม่จำเป็นต้องเป็นเครื่องหลักเสมอไป —
ตัวตามที่ตามหลังไม่กี่วินาทีก็ใช้ได้ และช่วยลดภาระเครื่องที่รับการเขียนจริง

### ต้นทุนที่เราสร้างให้เครื่องหลัก

| query | เวลา |
| --- | --- |
| กรองด้วย `date_visit` (ไม่มี index → full scan 237k แถว 88MB) | **380 ms** |
| กรองด้วยช่วง `vn` (PK range scan) | **7 ms** |
| อ่าน `cid` จาก `hn` | 2 ms |

7 ms ทุก 15 วินาที = ใช้เวลาเครื่อง **0.05%** และ `max_connections = 2000`
เราใช้ 1 connection ภาระจึงไม่ใช่เหตุผลที่ต้องย้ายไป replica อีกต่อไป

### ทำไมถึงแนะนำให้อยู่กับเครื่องหลัก

**replica lag เป็นปัญหาโดยตรงกับงานนี้** การแจ้งเตือนคิวต้องทันเวลา ถ้า replica ตาม
ช้า 30 วินาที ข้อความ “ใกล้ถึงคิว” จะไปถึงหลังคนไข้ถูกเรียกไปแล้ว และ lag มักแย่ที่สุด
ตอนโรงพยาบาลยุ่งที่สุด ซึ่งเป็นตอนที่ระบบต้องแม่นที่สุดพอดี

จะย้ายไป replica ก็ได้ถ้า **มีการเฝ้าดู lag และมั่นใจว่าต่ำกว่า ~10 วินาทีตลอด**
ถ้าไม่มีใครดู lag อยู่ อยู่กับเครื่องหลักปลอดภัยกว่า

สิ่งที่ป้องกันเครื่องหลักไว้แล้ว: user มีแค่ `SELECT` · `HosxpClient` ปฏิเสธ SQL
ที่ไม่ใช่การอ่าน · query ทุกตัวมีขอบเขต · ไม่มีการเขียนใด ๆ ลงฐาน HOSxP

## ที่ยังไม่ยืนยัน — ต้องถามเจ้าหน้าที่

1. **`status`** — พบค่า 1 กับ 2 เดาว่า 1 = รออยู่ 2 = เรียกแล้ว/เสร็จ แต่ยังไม่ยืนยัน
   ถ้าเดาผิดจะส่งแจ้งเตือนให้คนที่ตรวจเสร็จไปแล้ว
2. **`wait_dep`** — ค่าที่เห็นไม่สอดคล้องกับทั้ง "จำนวนนาทีที่รอ" และ "จำนวนคิวที่รอ"
   (dep 037 ได้ 60, 65, 70 เรียงตามเวลาเข้า ห่างกันทีละ 5) ถ้าไม่ใช่จำนวนคิวที่รอ
   ต้องนับเองด้วย `COUNT(*)` ในห้องเดียวกัน
3. **ห้องไหนควรแจ้งบ้าง** — `999 กลับบ้าน` และ `009 ตึกผู้ป่วยใน` ไม่ควรแจ้งแน่นอน
